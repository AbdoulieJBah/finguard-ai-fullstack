# FinGuard AI

FinGuard is a full-stack demo of a bank's operations and risk-intelligence workspace: an account ledger with authenticated, idempotent payments, plus credit, fraud and AML assessments, alerts, an audit trail and live dashboards.

> Demo software only. All data is simulated. It does not connect to payment rails and must not be used for real customer funds or production banking decisions.

**Stack:** Next.js 15 (React 19, TypeScript, Tailwind) · FastAPI · SQLAlchemy 2 · Alembic · PostgreSQL (Neon) · scikit-learn, pandas · pytest · GitHub Actions · Vercel + Railway

## What works

- **Authentication and roles.** PBKDF2-SHA256 password hashing (600,000 iterations), bearer sessions stored only as SHA-256 hashes, sign-out that revokes the session, and failed sign-ins recorded in the audit trail. Every data endpoint requires sign-in; the audit log is limited to Administrators and Compliance Officers.
- **Ledger and payments.** Balances in integer cents. A transfer is one database transaction: rows are locked in a fixed order, and the balance check and debit are a single statement, so concurrent payments cannot overdraw an account.
- **Idempotent payments.** Clients send an `Idempotency-Key` header. A retry with the same key (for example after a timeout) returns the original result instead of paying twice; reusing a key for a different payment is refused with 409.
- **Fraud model on every payment.** A fraud model trained on 2.77 million PaySim transactions scores each payment as it is made. Each score comes with an exact per-feature explanation, and high-risk payments open a fraud alert automatically. See [the model card](ml/MODEL_CARD.md) for data, validation and limitations.
- **Credit and AML assessments.** Rule-based scorecards return a score, a level, the reasons and a recommendation. Every assessment, model or rule, is stored with its inputs and engine version; high AML scores open an AML case.
- **Dashboards from real data.** Dashboard figures, six-month trends, the audit log and system health (database engine, round-trip latency, uptime) are computed from the database. The copilot answers from the same live figures.

### Honest limits (next steps)

- The fraud model is trained on **simulated** data (PaySim), whose fraud follows one dominant pattern; a one-line rule matches it at the High level, and real-world performance would be much lower. Credit and AML still use hand-written rules (`rules-1.0`).
- The copilot routes questions by keyword; an LLM with read-only database tools is planned.
- Alerts can be listed but not yet assigned or closed (case management is planned).
- The demo data (six months of assessments and alerts) is generated by a seeded simulation using the same rules as the live API.

## Fraud model

`ml/train_fraud_model.py` trains and evaluates the model; the API serves the exported scorecard (`backend/app/ml/fraud_scorecard.json`) with plain Python, so no ML libraries are needed in production.

- **Inputs** (all known when a payment is made): amount, sender balance before, share of the balance moved, hour of day, transaction type. PaySim's recipient-balance columns are excluded because they contain simulator artefacts.
- **Validation:** time-based split (train on earlier transactions, choose settings on the next period, test once on the latest period).
- **Model selection:** a binned logistic scorecard and gradient boosting, each with no rebalancing, class weights, random undersampling and SMOTE, compared on PR-AUC. The scorecard won on validation, and every score from it splits exactly into per-feature contributions (exact SHAP values for an additive model).
- **Honest baseline:** the model card reports simple rules next to the model and how many of the model's alerts they share.

To retrain, download PaySim from Kaggle (`ealaxi/paysim1`) and run:

```powershell
pip install -r ml/requirements.txt
python ml/train_fraud_model.py --data path\to\archive.zip
```

The script checks that the API's scorer reproduces the training predictions before it writes the model.

## Run locally

Requirements: Python 3.10+ and Node.js 20+.

```powershell
cd backend
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt -r requirements-dev.txt
python -m uvicorn main:app --reload
```

Without `DATABASE_URL` the API uses a local SQLite file (`backend/finguard_dev.db`). Migrations run and demo data is created automatically on start-up. API documentation: `http://localhost:8000/docs`.

In another terminal:

```powershell
cd frontend
Copy-Item .env.example .env.local
npm install
npm run dev
```

Open `http://localhost:3000/login`. Demo users (password `FinGuard123!`):

| Email | Role |
| --- | --- |
| `demo@finguard.ai` | Administrator (owns the demo accounts) |
| `analyst@finguard.ai` | Risk Analyst |
| `compliance@finguard.ai` | Compliance Officer |

## Configuration

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string (Neon, Railway, ...). `postgres://` and `postgresql://` forms are accepted. |
| `FINGUARD_CORS_ORIGINS` | Comma-separated frontend origins allowed to call the API. |
| `FINGUARD_SEED_DEMO` | `false` to start with an empty database. |
| `NEXT_PUBLIC_API_URL` | Frontend: the API's base URL. |

## Tests and CI

```powershell
cd backend
python -m pytest
```

The suite covers authentication, role checks, transfers (atomicity, insufficient funds, ownership, amount validation), idempotency, risk scoring, alerts and the dashboard figures. GitHub Actions runs it against both SQLite and PostgreSQL 16 on every push, and lints and builds the frontend. To run against PostgreSQL locally, set `TEST_DATABASE_URL`.

## Production hardening still needed

Before any real use: an identity provider with MFA, sign-in rate limiting, a secrets manager, encryption of sensitive fields, payment approval workflows (maker-checker), monitoring and alerting, and independent security and compliance testing.
